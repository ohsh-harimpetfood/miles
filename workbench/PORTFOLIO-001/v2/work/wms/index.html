01

FIELD REALITY

THE PROBLEM WAS PHYSICAL
BEFORE IT WAS DIGITAL.

창고의 위치, 품목, 재고 상태를 확인하는 과정이 랙카드와 현장 탐색, 사람 간 확인에 크게 의존하고 있었습니다.

위치와 품목 정보의 불일치, 재고 탐색의 번거로움, 실물과 시스템 재고를 다시 확인해야 하는 부담은 운영 규모가 커질수록 불확실성을 키웠습니다.

핵심 문제는 새로운 화면이 필요한 것이 아니라, 물리 창고의 상태를 더 신뢰할 수 있는 방식으로 디지털 상태와 연결해야 한다는 것이었습니다.

02

FIRST EXECUTABLE HYPOTHESIS

START SMALL ENOUGH
TO LEARN.

APPSHEET WAS THE FIRST EXECUTABLE HYPOTHESIS.

처음부터 custom WMS를 만드는 대신, Location / Item / Transaction 구조와 QR 기반 현장 흐름을 빠르게 실행해 볼 수 있는 형태로 시작했습니다.

AppSheet의 역할은 최종 기술을 결정하는 것이 아니라, 현장 개념과 데이터 모델, 모바일 작업 방식을 실제로 확인하는 것이었습니다.

03

CONSTRAINT / ARCHITECTURE PIVOT

THE MODEL HELD.
THE ARCHITECTURE HAD TO CHANGE.

UX CONTROL PERFORMANCE DEPLOYMENT FLEXIBILITY EXTENSIBILITY
APPSHEET→NEXT.JS→SUPABASE / POSTGRESQL→GIT→VERCEL

운영 요구가 늘어나면서 더 높은 UX 제어, 성능, 배포 유연성, 확장성이 필요해졌습니다.

초기에 검증한 현장 문제와 데이터 모델은 유지하되, 이를 더 확장 가능한 custom web architecture로 옮겼습니다.

이 전환은 WMS의 시작이 아니라, 이미 검증하기 시작한 운영 모델을 더 확장 가능한 구조로 옮긴 시점입니다.

04

OPERATING SYSTEM

NOT A FEATURE SET.
AN OPERATING FLOW.

INBOUND→INVENTORY→MOVEMENT→OUTBOUND→TRANSACTION HISTORY

기능을 각각 따로 만드는 대신, 입고부터 재고·이동·출고·이력까지 하나의 운영 흐름으로 연결했습니다.

거래 기록 주변에는 기준정보, 권한, 조정, 실사/정합성 확인 같은 운영 통제 구조를 배치했습니다.

현재 movement logic은 partial / full / merge handling과 packing-information preservation을 포함하며, 현장의 실제 물류 상태와 packaging constraint를 보존하는 방향으로 확장됐습니다.

05

PHYSICAL ↔ DIGITAL

THE WAREHOUSE HAD TO EXIST
THE SAME WAY IN BOTH WORLDS.

PHYSICAL LOCATION→MANAGED LOCATION IDENTITY→QR / RACK CARD→TRANSACTION→INVENTORY→DIGITAL MAP

Location을 단순한 문자열이 아니라 관리 가능한 공간 단위로 구조화하고, 이를 QR·랙카드·수불·재고·창고 맵과 연결했습니다.

현재 시스템은 location master / builder, QR / rack-card physical interface, warehouse map / occupancy visualization, mixed-stock location view와 서로 다른 storage topology를 지원합니다.

DOMAIN-LED UI DECISION

OPERATOR VIEWPOINT MATTERS.

화면이 데이터베이스 좌표를 그대로 보여주는 것보다 작업자가 실제 랙을 바라보는 방향과 일치하는 것이 중요했습니다.

일부 맵 표현에서는 작업자의 관찰 방향에 맞게 배열을 뒤집는 UI 결정을 적용했습니다.
